## 需求原文（逐字记录，未脑补）

> 补充能够自我升级的能力，update self。
> https://github.com/morning-start/git-tags/releases
> https://api.github.com/repos/xxx/xxxxx/releases/latest
>
> 或者用gh（如果有的话，优先用gh）
>  # GitHub CLI api
>  # https://cli.github.com/manual/gh_api
>
>  gh api \
>    -H "Accept: application/vnd.github+json" \
>    -H "X-GitHub-Api-Version: 2026-03-10" \
>    /repos/OWNER/REPO/releases/latest

**用户决策**：新增 `git-tags update` 子命令实现自我升级；查询最新版本时优先使用 `gh api`（本机已安装 gh，v2.97.0），gh 不可用或调用失败时回退 GitHub REST API（`https://api.github.com/repos/<owner>/<repo>/releases/latest`）。

## 背景与问题定性

- 现状：git-tags 通过 GitHub Actions 发布三平台 zip 资产（`git-tags-{goos}-{tag}.zip`，见 `.github/workflows/release.yaml`），但用户只能手动去 Releases 页面下载替换二进制。
- 自我升级是 CLI 工具的标准能力：本地版本落后于远端 release 时应能一键升级。

## 变更内容

1. 新增 `internal/selfupdate` 包：
   - `latestRelease(repo)`：优先 `gh api repos/<repo>/releases/latest`（继承本机 gh 登录态，天然规避 API 限流），失败回退 REST API；
   - `AssetName(goos, tag)` 与 release 工作流的 zip 命名严格对齐（`git-tags-windows-v2.5.0.zip`）；
   - 下载 zip → 内存解包 → 找到可执行文件（windows 下 `.exe`）→ 校验（解包成功且文件非空）→ 写同目录 `<二进制名>.update-<pid>.new` → 与旧二进制交换（Windows 上先把旧文件改名为 `.update-<pid>.old`，Unix 直接 overwrite）→ 清理 `.old`；
   - 当前版本取自 `cmd.RootCmd.Version`（由 `SetVersion` 注入，包内不硬编码）。
2. 新增 `git-tags update` 命令（分组：插件与版本管理）：
   - 默认：有新版 → 下载并替换，替换后提示重开终端使新版本生效；
   - `--check`：只查询比对，不下载不替换；
   - `--yes`：跳过确认直接安装；
   - `--repo owner/name`：显式指定仓库，缺省自动推断——优先读 git remote origin（仅 `github.com`），否则 `morning-start/git-tags`。
3. `cmd/root.go` 的 `Version` 常量保持既有角色（`.git-tags.toml` 的 govar 载体），运行时通过 `RootCmd.SetVersion` 把它传给 selfupdate。

## 决策记录

| 决策项 | 结论 |
|--------|------|
| 查询通道 | 优先 gh（用户指定），REST 兜底 |
| 资产匹配 | 与 release.yaml 的 zip 命名严格对齐；zip 内直接找可执行文件，不做平台目录假设 |
| 替换策略 | 同目录临时文件 + 交换（Windows 运行中文件不可覆盖删除，必须先改名腾位） |
| 仓库推断 | git remote origin（github.com）> 默认 morning-start/git-tags；`--repo` 可覆盖 |
