## 需求原文（逐字记录，未脑补）

> 现在有一个问题，就是有一些项目里会有一些lock文件，然后这些锁文件会自动根据配置文件更新版本，但是这些是不在gt的控制内的，gt已经提交了新版本的git。怎么处理这个问题？
> 1. 管理lock文件
> 2. lock在git tag后再自己提交
> 3. 添加一个gt命令，专门处理这种情况，把lock文件塞到之前提交的里面
> 哪个解决方法比较好？还是你有别的解决方法

**用户决策**：采纳方案 1「gt 管理 lock 文件」——gt 在发布（bump/set）写版本时同步 lock 文件根条目版本，随发布提交一起进入 tag 指向的 commit。

## 背景与问题定性

- 现状：4 个插件（node/flutter/uv/tauri）对 lock 文件（package-lock.json /
  pubspec.lock / uv.lock / Cargo.lock）只做**只读一致性校验、绝不写入**（README 亦以此为卖点）。
- 后果：gt 发布提交内 lock 版本滞后于配置文件 → 从 tag 检出时 lock 与配置文件不一致；
  下次 `npm install` 等工具链操作产生未暂存改动（工作区变脏）；下次 `gt bump` 被
  `EnsureInSync` 的 read() 校验直接阻断（node.lua L64-68 等），用户被迫手工重新生成再补提交。
- 行业对照：npm 官方 `npm version` 在同一提交内同步 package.json + package-lock.json
  （+ npm-shrinkwrap.json）再 commit + tag；semantic-release 因只改 package.json 造成
  同款漂移（issue #476、npm#340，后者证明 lockfileVersion 2/3 顶层与 packages[""] 两处都要改）。

## 变更内容（方案 1）

1. 4 个插件 `write()` 增加 lock 根条目版本同步，与新版本一并写入：
   - node：package-lock.json（lockfileVersion 2/3 顶层 `"version"` 与 `packages[""]` 两处；
     v1 仅顶层；npm-shrinkwrap.json 同）——**禁止全局 replace_all**，只改根条目，避免误伤同版本号依赖
   - flutter：pubspec.lock `root:` 块 version（保留 +build 语义）
   - uv：uv.lock 根包条目 version（name 取 [project].name）
   - tauri：src-tauri/Cargo.lock 根包条目 version
   - yarn.lock / pnpm-lock.yaml 无版本字段，无需同步（node 插件仅当 package-lock.json 存在时处理）
2. `read()` 一致性校验保留作为安全网，不动。
3. 引擎（internal/）零改动：`git add -A` 自动带 lock 进发布提交；`del` 回滚走
   `Sync → write()` 自动带回滚。
4. README「锁文件只读」卖点、sync-flow.svg 说明、各插件头部注释同步改写。

## 影响评估

| 项 | 值 |
|----|-----|
| 是否改库 | 否 |
