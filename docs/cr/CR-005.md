## 需求原文（逐字记录，未脑补）

> push动作前先做git push。是不是默认做了？
> git的流程中，push tag是不是也同时把commit也push了？
> 补上，需要先push commit然后才 push tag

**用户决策**：所有推送路径（`push` 命令、bump/set 的 `--push`）在推送 tag 之前，先推送当前分支的 commit（`git push <remote> HEAD`），成功后再推送 tag。

## 背景与问题定性

- 现状：`internal/git/git.go` 的 `Runner.PushTag` 只执行 `git push <branch> <tag>`——只推 tag 引用，不推分支 commit。
- 后果：发布流程的 `chore(release): bump to ...` 提交只在本地；tag 推上远端后，远端仓库里出现**只被 tag 引用、不被任何分支引用**的提交（"悬挂 commit"）。别人 clone 默认分支看不到该提交；若 tag 被删除，该提交沦为孤儿对象最终被远端 GC。
- 全部三个入口（`push` 命令 `cmd/root.go`、`Bump`/`Set` 的 `opts.Push`，`internal/core/engine.go`）都收敛到 `Runner.PushTag`，单点修改即可全链路生效。

## 变更内容

1. `internal/git/git.go` 的 `PushTag`：先执行 `git push <branch> HEAD`（推送当前分支 commit），成功后再执行 `git push <branch> <tag>`；任一步失败即整体报错返回（非快进/分叉时阻断 tag 推送，安全）。
2. 引擎与命令层零改动：`engine.go`、`cmd/root.go` 均不感知此变化。
3. README 的 `push` / `--push` 描述同步更新为「先推 commit、再推 tag」。

## 影响评估

| 项 | 值 |
|----|-----|
| 是否改库 | 否 |
| 是否重构 | 否 —— 单函数内增加一步 `git push <branch> HEAD` |
| 是否影响旧功能 | 是（行为变更）——所有推送路径从「只推 tag」变为「先推 commit 再推 tag」 |
| 是否影响旧用户 | 是——`--push`/`push` 现在会把分支 commit 一并推送；依赖「只推 tag、分支自行管理」的用户行为变化；本地无 remote 或分叉时推送会报错（此前推 tag 也会因无 remote 报错，分叉场景则由「tag 推送成功但 commit 缺失」变为「明确报错」） |
| 工时估算 | 极小（git.go 一处 + README 文案 + 手工验证） |
| 对排期影响 | 小 |

## 影响点清单（供 fst-review 变更针对性测试）

- 修改：`internal/git/git.go`（`PushTag` 增加 commit 推送步骤）
- 修改：`README.md`（push / --push 描述）
- 保留：`internal/core/engine.go`、`cmd/root.go`、`internal/lua/`、`plugins/` 不变
- 测试：真实/本地 bare remote 验证（① 有未推 commit：commit+tag 均到远端、分支前移；② 无新提交：`Everything up-to-date` 后仍推 tag；③ 本地分叉/落后：报错且不推 tag；④ 无 remote：报错信息清晰）；现有命令回归冒烟（ls / patch --dry-run / check）

## 决策记录

| 决策项 | 结论 |
|--------|------|
| 顺序 | 先推 commit、后推 tag（用户指定）；避免远端出现只被 tag 引用的悬挂提交 |
| commit 推送写法 | `git push <branch> HEAD`（推送当前分支到远端同名分支），不硬编码分支名 |
| 分级 / 排期 | 中度 / 立即实施（用户确认） |
